# General (not yet classified)

The system must produce a log message for every file that it scans.

The log message that the system generates, must contain these items:
* ISO8601 date (`yyyy-MM-dd`)
* ISO8601 time (`HH:mm:ss.fff+zzz`, this is the time in UTC with timezone offset in three-digit minutes)
* system name
* process id
* thread id
* malware id (from the Marlock signature database)
* file name
* file size
* file checksum (SHA256)
* scan duration in seconds
* the authenticated user that wanted the system to scan the file.

The system must be available on an SLA level of 3. This is defined in the SLA of the organisation.

# Functional Suitability

The system must detect malware.

The system accepts files and examines these files.

The user can send more than one file at the same time.

> What specific types of malware (e.g., viruses, ransomware, spyware) must the system be capable of detecting and quarantining?

Malware has one of these types:
* Virus
* Ransomware
* Spyware

When the system finds malware in a file, the system must put the file into a special folder with the name 'quarantine'.

> What actions should be triggered if malware is detected (e.g., notification to administrator, automatic removal, blocking access)?

When the system examines malware in a file, the system must tell the user that the result of the test. Note: The Logging Service will make notifications to the organisation if necessary.

When a file in in the 'quarantine' folder, the system will remove the file after 30 days.

> How frequently must the malware signature database be updated, and what is the process for updating it?

The system must update the malware signatures every 30 minutes. When the system updates the malware signatures, the system must continue to be available to the user.

# Performance Efficiency

The system must be able to examine files with a size up to a maximum of 50 MB.
The system must be able to examine 1000 files at the same time.
The system must be able to examine multiple files with a total size of 1024 MB per second.
For 95 % of all files the system must complete the test in 2 seconds.

> What are the acceptable limits for CPU, memory, and disk I/O utilization during peak scanning operations?

The system can make full use of the CPU, memory and disk.

> Under what specific hardware and software environment conditions are the performance metrics (50 MB file size, 10000 files concurrently, 1024 MB/second throughput) expected to be met?

The performance metrics hold true for 95 % of all operations.

When the maximum number of files that the system can examine increases, the system must be able to extend the capacity. 

# Compatibility

The log message must be in a SYSLOG compatible format.

> Which specific version or profile of SYSLOG (e.g., RFC 3164, RFC 5424) must the log message format comply with?

The format of the log message is compatible with RFC 5424.

The system must have an HTTP REST interface. The REST interface must be compatible with ODATA version 4.
The system must have an HTTP SOAP interface.

> Will the REST and SOAP interfaces require authentication and authorization mechanisms, and if so, what standards or protocols should be supported (e.g., OAuth, API keys)?

The system accepts identification through OAuth.

When a user wants to use the system, the user must identify himself.

> Are there any specific external systems (e.g., SIEM, user directory) that the malware scanner must integrate with, and what are their respective interface requirements?

The system must connect to the LDAP service of the organisation.

# Interaction Capability

> Will there be a user interface or administrative console for managing the malware scanner, and if so, what are the primary tasks users will perform through it?

The system has an administrative console. The 'administrators' role can use this console to operate these tasks:
* stop the service
* start the service
* pause the service
* make part of the service active
* make part of the service not active
* remove a file from the `quarantine` folder.

> Are there any specific accessibility requirements (e.g., for visually impaired administrators) for any user-facing components of the system?

The system is a web service. That is why there are no specific accessibility requirements for user facing components. The administrative console must be easy to operate by visually impaired people.

The REST interface must have a Swagger implementation. With this a user can easily learn how to operate the system.

# Reliability

> What are the mean time between failures (MTBF) and mean time to repair (MTTR) targets for the system?

> What fault tolerance mechanisms (e.g., redundancy, failover) must be implemented to ensure continuous operation in the event of hardware or software failures?

The system consists of multiple nodes that operate on Kubernetes. A load-balancer will put the files from the user to the nodes.

# Maintainability 

When the system examines the EICAR test virus file, the system must give a result that this the file is a virus. Also, the system must operate as with any other malware.
